# 闲鱼卖家工作台项目蓝图

## 项目目标

在一个可自托管的工作台中管理卖家账号、商品、订单、库存、消息和经营数据。优先保证数据隔离、动作可追踪、异常可恢复；平台接口发生变化时，应能替换闲鱼适配层，而不需要重写业务规则。

## 当前代码基线

- 直接上游：[`23Star/xianyu-super-butler`](https://github.com/23Star/xianyu-super-butler)，本地初始提交为 `c73d755`。
- 上游声明其基于 [`zhinianboke/xianyu-auto-reply`](https://github.com/zhinianboke/xianyu-auto-reply) 二次开发；原有来源说明和 `LICENSE` 保留。
- 当前已有能力以根目录 README 为准，包括账号、商品、订单、卡密、消息、自动/AI 回复、通知和运营看板。
- 这是已有 AGPL-3.0 代码的衍生工作副本，不代表下列其他仓库的代码已复制或功能已接入。

## 目标边界

1. **业务模块**：账号、商品、订单、库存、消息、回复策略和通知各自维护数据与服务边界。
2. **闲鱼适配层**：集中封装平台请求、会话状态、解析和 DTO；业务代码不散落私有协议字段。
3. **动作分类**：只读、可重复写入和不可轻易撤回的动作分开登记；写操作校验归属、输入与幂等键，并留下审计记录。
4. **市场洞察**：商品检索、价格历史和告警单独运行；默认只读，不触发发布、聊天、订单或账号操作。
5. **可选自动化入口**：先稳定服务接口，再考虑 CLI/MCP；自动化入口必须复用同一权限、限流和审计逻辑。

## 参考项目的功能细化

参考 [Ydisks-Xianyu-Helper](https://github.com/Christ9038/Ydisks-Xianyu-Helper) 的公开 README 和 Wiki，重点对照其[自动化发货与回复](https://github.com/Christ9038/Ydisks-Xianyu-Helper/blob/main/docs/wiki/Automated-Delivery-and-Replies.md)、[在线聊天与账号任务](https://github.com/Christ9038/Ydisks-Xianyu-Helper/blob/main/docs/wiki/Chat-and-Account-Automation.md)、[批量铺货](https://github.com/Christ9038/Ydisks-Xianyu-Helper/blob/main/docs/wiki/Bulk-Listing.md)及[部署与数据库](https://github.com/Christ9038/Ydisks-Xianyu-Helper/blob/main/docs/wiki/Deployment-and-Database.md)文档，吸收其可操作的业务流程、异常处理和运维设计；这里只借鉴产品设计，不复制其实现。下列内容是候选升级项，不代表当前版本已经提供。

### P0：自动化执行可追踪、可恢复

- 将规则拆成明确的触发器和有序动作。候选触发器包括未付款改价、付款发货、评价赠品、发货后评价提醒；每条规则至少绑定账号，并按需绑定商品/规格、库存组、每件数量、延时和启用状态。
- 每次触发建立执行记录，保存订单/消息来源、规则快照、当前步骤、开始/结束时间、结果和脱敏后的失败原因；对同一业务事件建立幂等键，避免 WebSocket 重连、重复事件或任务恢复造成重复发货/发消息。
- 建立异常与延迟任务工作区，按待处理、执行中、成功、失败、需人工核对分类；支持查看订单、库存、消息历史和失败步骤，再由操作者决定重试或完成处理。
- 对“请求已发出但结果未知”的动作禁止直接自动重发；先回读平台状态或转人工核对。重试采用有限次数、退避和冷却；恢复任务只续跑已确认安全的剩余步骤。
- 对可能漏掉实时付款事件的情况，先记录本地订单状态，经过可配置宽限期再进行有限补偿检查；若已有对应执行记录则不重复触发。任何补偿路径均须通过离线测试和小额测试订单验证。
- **验收标准：**同一事件重复投递多次只产生一次有效交付；在每个动作边界模拟进程退出后可恢复；状态不确定时不会重复向买家发送内容；操作者可以从记录中判断是否需要人工介入。

### P0：账号隔离、会话一致性与账号级任务

- 账号是监听器、会话列表、消息状态、自动化规则和任务记录的隔离边界；启动、停止、断线、重连、续期失败、暂停和手动恢复均应有显式状态及最近错误。
- 消息中心重连后以本地持久化记录和平台历史补齐为准，而不是只依赖 WebSocket 在线期间收到的事件；按账号分别加载联系人、消息历史和实时消息。
- 把平台系统通知/交易卡与买家普通消息分流：系统事件进入订单或自动化决策，不进入关键词、默认或 AI 买家回复链。消息解析无法确定类型时默认不触发高影响自动动作，并留下诊断记录。
- 账号级自动任务（如每日商品维护或平台允许的订单后续处理）需定义时区、执行窗口、每日次数、暂停条件、手动执行、幂等标识和逐项结果；部分失败只重试失败项，不能用“任务已启动”冒充全部成功。
- 凭据续期失败应记录原因和冷却状态，避免频繁重试或要求账号所有者不断重新登录；需人工验证时明确提示并停止相关写操作。
- **验收标准：**多账号并发事件不会串消息或串库存；重复任务不会对同一订单/日期重复处理；暂停或停用账号不会继续触发后台任务；重连后的会话历史可校准。

### P1：可预览、可审计的发货模板与库存流程

- 将多段发货消息做成可复用模板，支持有序文本/图片/卡密组动作、订单/买家/卡密等受限变量、每步延时和启停；明确哪些规则可使用模板，避免不同触发器误共用配置。
- 明确数量语义：卡密配置按“每件商品数量”，再乘订单购买数量；保存前展示预计扣库量，并检查账号、商品规格与库存组的归属关系。
- 为并发订单定义库存预留/扣减和失败补偿规则，执行记录中显示预留、已发送、已确认、已释放数量；禁止因失败重试重复扣库或把已发送卡密重新入库。
- 手动补发前展示买家、订单、商品、历史发货动作和库存变化；要求操作者确认并填写处理原因，完成后再次核对库存与订单状态。
- **验收标准：**多规格、多数量订单的卡密数量正确；并发不超卖；失败和恢复不会重复发卡；所有手动补发均有操作者与原因记录。

### P1：批量商品操作采用“预检—确认—后台任务”

- 若新增批量导入/发布，支持 CSV/XLSX/TSV 模板和可选图片包；先校验列名、价格、库存、邮费、图片路径、账号权限、商品规格与关联自动化配置，再展示逐行预检结果。
- 分类策略需能区分用户显式指定、界面选择、平台建议和兜底值；不得用兜底掩盖超时、鉴权失败、风控或响应解析失败。类目字段须整体校验，避免半套类目数据被静默接受。
- 通过预检后才创建后台批次；逐行记录排队、提交中、成功、失败、取消和可重试状态。支持查看进度、取消尚未提交的行、只重试明确可重试的失败行，并导出结果表。
- 上传文件需限制大小、图片数量和解压路径；拒绝绝对路径、`..` 路径及不支持格式。每批数量上限应根据本项目资源和平台规则压测后确定，不直接照搬参考项目的数值。
- 新批量写操作默认关闭；先提供模板下载、预检和只读结果查看，再经用户显式确认提交。首轮验收使用单行/测试商品，不在 CI 使用真实账号发布。
- **验收标准：**错误行不提交、有效行状态可追踪；中断后可识别已提交行并安全续跑；重试不会重复发布；恶意压缩包路径无法写出指定目录。

### P1：AI、通知与可观测性形成闭环

- AI 回复配置增加模型/端点连通性测试和明确的测试结果；回复决策链有顺序、适用范围和审计原因。AI 仅处理被允许的场景，未命中、超时、无效输出或越过议价边界时转入安全兜底，不得绕过最低价、最大议价轮数和账号开关。
- 通知渠道与账号、事件类别绑定；提供测试通知、失败状态和脱敏后的投递记录。自动化完成、失败、需人工处理等事件应按类别独立订阅，通知失败不能反向重复执行交易动作。
- 看板从可验证的业务事件汇总执行数、成功/失败数、待处理异常和库存风险；点击指标可追溯到具体账号、订单和执行记录，不以空数据或缓存值掩盖采集失败。
- **验收标准：**无效 AI 回复不会直接发送；通知失败有独立可重试记录；看板数据可追溯到明细且显示数据更新时间。

### P2：备份、迁移与发布体验

- 为数据库结构引入版本化迁移；升级前提供备份步骤并检查备份成功，提供恢复演练文档。SQLite 备份需考虑 WAL 一致性，不能在写入时只复制主数据库文件。
- 评估 Cookie、Token、卡密、AI/SMTP/通知凭据的静态加密，制定加密密钥生成、权限、备份与轮换策略；密钥丢失时应明确数据不可解密，不能悄悄回退为明文。
- 保持 Docker Compose 为当前主要交付方式；先完善健康检查、版本/提交号展示、镜像架构覆盖、固定版本标签和升级回滚说明，再按实际用户需求评估桌面安装包/托盘控制器。
- **验收标准：**从上一版本备份可恢复并完成迁移；错误密钥会显式报错；发布镜像可识别版本与架构，且升级失败有已验证的恢复步骤。

### 实施顺序与范围控制

1. 先做 P0 的执行记录、幂等键、异常处置和账号隔离测试，优先覆盖现有自动发货、订单及消息链路。
2. 再做 P1 模板库存语义、AI/通知闭环；批量发布单独立项，先预检后小批量灰度，未经用户确认不启用写入。
3. 最后做 P2 迁移与发布升级；数据库更换、Go 重写、桌面托盘、多渠道复杂自动化均不作为当前前置条件。
4. 每个里程碑先交付脱敏 fixture/mock 的单元与恢复测试，再由账号所有者在符合平台规则的测试账号上显式验证；全程保留人工暂停和人工接管入口。
